## Current Feature

Order drafts and submission: retailers build shared drafts, save them with version checks, and submit them with price review. Submission freezes the ordered SKU, name, language, edition, prices, and totals. Retailers can cancel a whole draft or submitted order. Nothing reserves stock yet; staff confirmation and rejection with reservation are the next feature.

## Status

Completed — merged to `main` as `6665eaa` (2026-09-30).

## Goal

A retailer adds catalog variants to a draft shared by their organization, edits quantities, saves, and submits after reviewing prices. A submitted order keeps its frozen snapshot regardless of later catalog changes. Retailers can cancel a draft or a submitted order. Distributor staff can read all orders; their processing screens come next.

## Scope and decisions (2026-09-30)

- Branch: `feature/order-drafts`.
- **Statuses in this slice:** `draft`, `submitted`, `cancelled`. `rejected`, `confirmed`, and the shipment statuses arrive with their workflows (overview §5).
- **Drafts:**
  - A retailer organization can have several drafts. Every retailer user in the organization can see and edit them.
  - Staff have read-only access to all orders. Staff cannot create, edit, submit, or cancel.
- **Order numbers:** human-readable and unique (`PO-001001`, generated by the database), used to scope UI selectors.
- **Line limits:** one line per variant; quantity 1–10,000; at most 100 lines per order.
- **Adding to a draft:** a variant can be added only while it is visible in the catalog (active product and variant). A line whose variant later becomes hidden stays in the draft, is flagged unavailable, and blocks submission until it is removed.
- **Prices:**
  - Draft prices are provisional and always read from the current catalog.
  - Submission compares the prices the retailer reviewed with the current prices. Any difference returns 409 `PRICE_CHANGED`, and nothing is submitted.
- **Retailer cancellation:** cancelling a draft or submitted order is auto-approved and attributed to the retailer. The reason is optional. Cancelling confirmed orders is a later feature.
- **Out of scope:** staff confirm/reject, reservations, shipments, returns, notifications, order search beyond the status filter.

## Data and invariants

### Order

- Fields: ID, number, retailer organization, status, `version` (starts at 1 and increases with every mutation), currency (`EUR`), creator, timestamps, submitter and submission time, canceller, cancellation time and reason, and `totalMinor`.
- `totalMinor` stays null until submission, when it is frozen.
- **Database rules:**
  - An order belongs to a retailer organization (trigger).
  - Status and the timestamp/actor columns must match (CHECK):
    - draft: no submission or cancellation data;
    - submitted: submission data and a total;
    - cancelled: cancellation data.

### OrderLine

- Fields: order, variant, quantity, and snapshot columns: SKU, product name, language, edition, unit price, and line total (BIGINT).
- Snapshot columns are either all null (draft) or all set (submitted), with `line total = unit price × quantity`.
- Lines can be inserted, updated, or deleted only while their order is a draft (trigger). Submission writes the snapshot before changing the status, in the same transaction.
- Unique per order and variant.

## Consistency rules (overview §7)

- **Idempotency-Key** (same machinery as inventory) is required for draft creation, submission, and cancellation.
  - Draft creation is scoped by organization and actor, with no target.
  - Submission and cancellation are scoped to the order.
- **Versions:** every draft mutation (save lines, submit, cancel) sends the current `version`. A stale version returns 409 `VERSION_CONFLICT` and changes nothing.
- **Transactions:** every order mutation runs in a Serializable transaction with bounded retry and writes its audit event atomically.
- **Order of checks:**
  1. The order is missing or belongs to another organization → 404 `NOT_FOUND`.
  2. The status does not allow the action → 409 `INVALID_ORDER_TRANSITION`.
  3. The version is stale → 409 `VERSION_CONFLICT`.
  4. The input is invalid → 422 `VALIDATION_FAILED`.
  5. Business checks fail → 409 `VARIANT_UNAVAILABLE` or `PRICE_CHANGED`.

## API contract

| Endpoint | Access | Behavior |
|---|---|---|
| `GET /api/orders` | Retailer (own organization), staff (all) | Paginated summaries; `status` filter; newest first |
| `GET /api/orders/:orderId` | Retailer (own organization), staff (all) | Detail with lines |
| `POST /api/orders` | Retailer + CSRF + Idempotency-Key | Create a draft, optionally with lines; 201 |
| `PUT /api/orders/:orderId/lines` | Retailer + CSRF | Replace the draft's lines (`version`, `lines`); 200 |
| `POST /api/orders/:orderId/submit` | Retailer + CSRF + Idempotency-Key | `version` and `reviewedPrices` for every line; 200 |
| `POST /api/orders/:orderId/cancel` | Retailer + CSRF + Idempotency-Key | `version`, optional `reason`; 200 |

- **Lines in responses:** each has variant, SKU, product name, language, edition, quantity, unit price, and line total. Draft lines also report `isAvailable` and the current `availableQuantity`, which is informational only.
  - `priceStatus` is `provisional` for drafts and `frozen` once submitted.
  - Lines sort by SKU.
- **Validation:** duplicate variants, too many lines, invalid quantities, unknown variants, and submitting an empty draft return 422 with field details.
- **Pagination** follows the catalog. Sort order: `createdAt` descending, then ID descending.

## Audit

- One audit event per mutation, entity `order`, actions `created`, `lines_updated`, `submitted`, `cancelled`. Each event records the before/after status, version, line count, and total where relevant. No-op saves (identical lines) still advance the version, because the client asked to save, and they are audited.

## UI acceptance criteria

- **Retailer navigation:** Orders (`/orders`). Retailers still land on the catalog.
- **Catalog product details (retailers):** after selecting a variant, choose a quantity and a target draft (an existing draft or "New draft"), then **Add to draft**. Success links to the draft.
- **`/orders`:** the organization's orders with number, status, line count, total (marked as an estimate for drafts), and last update; a **New draft** button; a status filter; pagination.
- **`/orders/:orderId` as a draft:**
  - Editable quantities and line removal, with current prices, line totals, and availability flags.
  - **Save draft** and **Submit order**. Submitting needs saved changes and shows a confirmation that explains it does not reserve stock.
  - **Cancel order**.
  - A version conflict keeps the local edits on screen and offers **Reload latest**. A price change shows the affected SKUs and reloads the new prices for review.
- **Submitted or cancelled orders:** read-only frozen lines and total, status history (created / submitted / cancelled with actor and time), and **Cancel order** for submitted orders.
- **Behavior and accessibility:**
  - Forms preserve input on errors, prevent double submission, and invalidate order and catalog queries after success.
  - Semantic HTML, keyboard access, visible focus, and a usable narrow layout.
- **Selectors:** `data-test` attributes; rows scoped by `data-order-number` and lines by `data-sku`.

## Deterministic seed

Created only if missing; orders changed later by users are never overwritten.

| Number | Organization | Status | Lines |
|---|---|---|---|
| `PO-000001` | Tabletop Lantern | draft | `LOV-EN-STD` × 4, `SWA-GI-EN` × 2 |
| `PO-000002` | Tabletop Lantern | submitted (frozen) | `CWO-EN-STD` × 3 at 3500, `TKC-EN-STD` × 10 at 0 |
| `PO-000003` | Tabletop Lantern | cancelled (from draft) | `MBM-SR-STD` × 1 |
| `PO-000004` | Cardboard Keep | draft | `LOV-SR-STD` × 6 |

New orders are numbered from `PO-001001`, so they never collide with seed numbers.

## Verification

- **Access:**
  - Retailers see only their own organization's orders; another organization's order returns 404 on every endpoint.
  - Staff can read but get 403 on mutations. Unauthenticated requests get 401. Missing CSRF gets 403.
- **Drafts:**
  - Create with and without lines (idempotent); replace lines.
  - Validation: duplicates, limits, hidden variants on add, unknown variants.
  - A stale version returns `VERSION_CONFLICT` with no change.
  - A hidden variant blocks submission with `VARIANT_UNAVAILABLE`.
- **Submission:**
  - Frozen snapshot and total. Later catalog price and name changes do not alter the submitted order.
  - `PRICE_CHANGED` when a reviewed price differs; an empty draft returns 422.
  - Replaying the same key returns the same response. After submission, lines cannot change: the API returns `INVALID_ORDER_TRANSITION`, and direct SQL is rejected by the trigger.
- **Cancellation:** from draft and from submitted; `INVALID_ORDER_TRANSITION` when already cancelled; attributed to the actor.
- **Concurrency:** two parallel saves with the same version produce exactly one success. The loser returns 409 `VERSION_CONFLICT`, or `CONCURRENT_MODIFICATION` if the shared three-attempt Serializable retry budget is exhausted. Retrying the stale version after the race returns `VERSION_CONFLICT`; neither failed request overwrites the winner or adds audit. This clarification (2026-10-01, PR #6) aligns the feature criterion with the overview's bounded-retry contract; no API behavior changes.
- **Rollback:** an injected audit failure leaves no change and no idempotency record.
- **Stock:** no reservation or inventory movement is created by any order action.
- **Seed:** rerunning it creates nothing new.
- **Browser:**
  - Add a line from the catalog; edit and save; handle a version conflict from a second tab; submit with the no-reservation confirmation; handle a price change; cancel.
  - Read-only submitted view; keyboard access; narrow layout; retailer isolation; login/logout regression.
- `pnpm typecheck`, `pnpm lint`, `pnpm build` pass. Record actual results and gaps.

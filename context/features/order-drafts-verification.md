# Order drafts and submission: verification and handoff

## Implemented scope

- **Orders and lines:** `Order` and `OrderLine` with statuses `draft`, `submitted`, `cancelled`. Order numbers are generated by the database (`PO-001001` onwards; lower numbers are reserved for seed orders).
- **Retailer actions** (own organization only):
  - create a draft;
  - replace the draft's lines, with a version check;
  - submit after reviewing prices, which freezes the lines and total;
  - cancel a draft or a submitted order.
- **Staff access:** read-only access to every organization's orders, through the API and the `/orders` pages.
- **Consistency:** create, submit, and cancel reuse the inventory feature's machinery (`IdempotencyService`, `runSerializable`, `recordAudit`). Saving lines is Serializable and version-checked but needs no idempotency key. `IdempotencyService.execute` now records the real response status (200 or 201).
- **Web:**
  - Orders navigation for retailers; `/orders` list with a status filter.
  - `/orders/:orderId`: draft editor, or a read-only frozen view with history.
  - **Add to draft** on catalog product details: choose a quantity, then an existing draft or a new one.
- **Seed:** `PO-000001`–`PO-000004` (drafts, a submitted order, a cancelled order), created only if missing.
- No stock is reserved or moved by any order action. Confirmation and rejection with reservation are the next feature.

## Design decisions

- **Database backstops:**
  - An order must belong to a retailer organization.
  - Order identity (number, organization, creator, currency) is immutable.
  - The status and its lifecycle data must match (CHECK).
  - A frozen total cannot change, and a cancelled order cannot change at all.
  - On submission, the order must have lines, every line needs a snapshot, and the total must equal the sum of line totals.
  - Lines can change only while the order is a draft.
  - A line snapshot is all-null or all-set, and its line total must be exact.
- **Draft pricing:** draft lines read the live catalog. Submission compares `reviewedPrices` with the current prices, then copies SKU, product name, language, edition, unit price, and line total into the line. Totals are BIGINT.
- **Hidden variants:** a line whose variant became hidden stays in the draft, is flagged `isAvailable: false`, and blocks submission with `VARIANT_UNAVAILABLE`. Adding a hidden variant is rejected with 422.
- **Error precedence:** 404 → `INVALID_ORDER_TRANSITION` → `VERSION_CONFLICT` → 422 → `VARIANT_UNAVAILABLE` / `PRICE_CHANGED`.
- **Draft editor state:** the editor holds local edits against the version it loaded. Background refreshes replace the edits only when nothing is unsaved. A conflict keeps the edits on screen and offers **Reload latest**. A price change reloads the order, so the retailer reviews the actual new prices before resubmitting.
- **Add to draft:** reads the draft, merges the quantity, and saves with the draft's version. Only creating a new draft uses an idempotency key.
- **Migration order:** the migration is named `20260930140000_order_drafts` so it sorts after inventory. It creates `orders_number_seq` (starting at 1001) before the table that uses it.

## API / PostgreSQL checks

`apps/api/checks/orders.mjs` (`pnpm --filter @pandora/api check:orders`) runs against a new, empty QA database. It uses port 3014 by default (`ORDERS_CHECK_PORT`).

```sh
docker compose exec -T postgres sh -c 'createdb -U "$POSTGRES_USER" pandora_orders_check_unique'
ORDERS_CHECK_DATABASE=pandora_orders_check_unique pnpm --filter @pandora/api check:orders
```

Covered groups (16):

1. **Seed:** statuses, frozen `PO-000002` (total 10500 with exact line totals), drafts unfrozen; a reseed adds nothing and writes no audit.
2. **Isolation:** retailers list only their own organization; another organization's order returns 404 on read, save, submit, and cancel. Staff read all orders but get 403 on mutations. Missing CSRF → 403; no session → 401; no side effects.
3. **Create:** a missing key returns 400; a replay returns the same order; a reused key with another payload returns 409. Numbering starts at `PO-001001`, and an audit event is written.
4. **Line validation:** duplicates, 101 lines, quantities 0 / 10,001 / 1.5, unknown variant, hidden variant or product, unknown field, and missing version all return 422 without changes.
5. **Save lines:** replace, add, and remove work; the version increments; a stale version returns `VERSION_CONFLICT` with no change; the save is audited.
6. **Hidden variant in a draft:** a variant hidden after being added stays in the draft, is flagged, and blocks submission with `VARIANT_UNAVAILABLE`.
7. **Submit:** incomplete reviewed prices or an empty draft return 422; price drift returns `PRICE_CHANGED`; a correct submission freezes the snapshot and total. A replay returns the identical body. Saving or submitting again afterwards returns `INVALID_ORDER_TRANSITION`.
8. **Frozen after submission:** catalog price, edition, and name changes after submission do not change the submitted order.
9. **Cancel:** works from a draft (the reason is trimmed) and from a submitted order (the frozen total is kept), attributed to the actor; a repeated cancel returns `INVALID_ORDER_TRANSITION` and a stale version returns `VERSION_CONFLICT`.
10. **Concurrency, saves:** two parallel saves with the same version give exactly one 200 and one 409 (`VERSION_CONFLICT`, or `CONCURRENT_MODIFICATION` after exhaustion of the shared retry budget). Persisted lines match the winner, the version advances once and one audit is written. A subsequent stale-version retry returns `VERSION_CONFLICT` without changing the order or audit. Clarified in PR #6 after CI exercised retry exhaustion; API behavior is unchanged.
11. **Concurrency, submissions:** five parallel identical submissions with one key submit once (one version increment, one audit event).
12. **Rollback:** an injected audit failure returns 500 and leaves the draft unsubmitted and unfrozen, with no idempotency record; the same key then succeeds.
13. **Database constraints:** these direct SQL writes are rejected:
    - updating, deleting, or inserting lines on a submitted order;
    - changing a frozen total;
    - creating an order for the distributor;
    - submitting an empty order;
    - editing a cancelled order.
14. **No stock effects:** no inventory quantity or movement changes across all order actions.
15. **List:** status filter, pagination, newest first; invalid filters and IDs return 422; an unknown ID returns 404.
16. **OpenAPI and logs:** all order routes are documented with the `Idempotency-Key` header on create, submit, and cancel, and the logs contain no credentials or tokens.

## Browser checks

The browser scripts share the no-dependency Chrome driver in `apps/web/checks/cdp.mjs`; `inventory-browser.mjs` now uses it too. `apps/web/checks/orders-browser.mjs` needs a freshly seeded QA stack, set up the same way as the inventory browser checks (API on 3013 against the QA database, `API_PORT=3013 pnpm --filter @pandora/web dev --port 5175 --strictPort`), then:

```sh
node --env-file=.env apps/web/checks/orders-browser.mjs
```

Covered groups (11):

1. **Orders list:** the retailer sees their organization's orders with written-out statuses and estimated draft totals.
2. **Add to an existing draft:** from the catalog; the default draft is the latest one, quantities merge (4 + 2 = 6), and the message says stock is not reserved.
3. **Draft editor:** an invalid quantity is flagged and submission is disabled while unsaved; a save succeeds and updates the total.
4. **Version conflict:** a second session saves first; the local edit stays visible; **Reload latest** shows the other session's quantities.
5. **Submission with a price change:** an administrator changes a price, so submitting reports `PRICE_CHANGED` for the SKU and shows the new price. Resubmitting after the confirmation (which states that submitting does not reserve stock) freezes the order: read-only lines and a "Submitted by" history entry.
6. **New draft and cancellation:** adding to "New draft" creates `PO-001001`; cancelling it with a reason records the reason in the history.
7. **Cancel a submitted order:** `PO-000002` is cancelled from its page and keeps its frozen total.
8. **Keyboard:** the add-to-draft controls are reachable with Tab and show a visible focus outline.
9. **Narrow layout:** at 390px the list and order page have no horizontal page overflow.
10. **Isolation:** another retailer sees only its own order; opening another organization's order shows "does not exist".
11. **Staff and page errors:** the operator sees all orders with a Retailer column and no create, edit, or cancel controls; no page errors were raised.

Screenshots are saved to `$TMPDIR/pandora-orders-evidence` (`ORDERS_CHECK_EVIDENCE` overrides this).

## Selector contract

Rows are scoped by `data-order-number` and lines by `data-sku`.

- **Navigation:** `orders-nav`.
- **List:**
  - Actions and errors: `order-create`, `order-create-error`, `orders-retry`.
  - Filter and results: `orders-status-filter`, `orders-total`.
  - Rows: `order-row`, `order-link`, `order-status`.
  - Paging: `orders-page`, `orders-previous`, `orders-next`.
- **Order page:**
  - Header and lines: `order-number`, `order-status`, `order-line`, `order-line-quantity`, `order-line-remove`, `order-line-unavailable`, `order-total`.
  - Saving and conflicts: `order-save`, `order-save-success`, `order-save-error`, `order-conflict`, `order-reload`.
  - Submitting: `order-submit`, `order-submit-panel`, `order-submit-no-reservation`, `order-submit-confirm`, `order-submit-error`.
  - Cancelling: `order-cancel`, `order-cancel-panel`, `order-cancel-reason`, `order-cancel-confirm`, `order-cancel-error`.
  - Other: `order-history`, `order-browse-catalog`.
- **Catalog:** `add-to-draft-panel`, `add-quantity`, `add-draft-select`, `add-to-draft`, `add-to-draft-success`, `add-to-draft-link`, `add-to-draft-error`.

Intentional semantic-locator exceptions: the back link, the "Back to draft" and "Keep order" buttons, and the retry button on the order-loading error. Status and error text is also reachable via `role=status` / `role=alert`.

## Results — 2026-09-30

- **API/PostgreSQL:** all 16 groups passed on three fresh QA databases (`pandora_orders_check_20260930_114102`, then `…_r2` and `…_r3`).
- **Regressions on fresh databases:** inventory 18 of 18, catalog 11 of 11.
- **Browser:** orders 11 of 11 and inventory 9 of 9 on two fresh QA stacks (`pandora_orders_browser_20260930_114328` and `…_114436_r2`); the second run executed the suites in the opposite order. Screenshots were inspected: list, draft editor, submitted view, and narrow view.
- **Found and fixed during verification:** the order browser script checked the default draft before the draft list had loaded. The app already disables the controls during loading, so the script now waits for them.
- **Development database:** the additive migration was applied without a reset, and the seed ran twice (4, then 0 new demo orders).
- **Final gates:** `pnpm typecheck`, `pnpm lint`, `pnpm build`, and `git diff --check` pass. The existing non-failing chunk-size warning remains.

## Limitations and follow-ups

- Staff have read-only order pages. Processing screens for staff (confirm/reject with reservation) are the next feature, and so is the operator landing page for orders awaiting processing.
- On narrow screens, order tables scroll inside their container, and long SKUs wrap.
- A cancelled draft (never submitted) shows its lines at current catalog prices, labelled as an estimate.
- Adding from the catalog to a draft whose version changed returns a conflict message; the retailer retries, and there is no automatic merge.
- Carried over: login rate limiting, session cleanup, test/CI setup, audit foreign keys, shared UI primitives (orders also reuse catalog styles), and the Playwright catalog browser harness, which was not re-run.
